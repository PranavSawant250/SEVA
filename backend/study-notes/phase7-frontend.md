# Phase 7 — Frontend UI (React SPA & Design System)

## Overview
Phase 7 delivers SEVA's complete, single-page client interface built with React 18 and Tailwind CSS v3. The frontend interfaces seamlessly with all Node/Express backend services established in Phases 1–6, exposing daily day plan generation, email workload ingestion, conversational AI chat, timetable configuration, and end-of-day reflection through a dynamic, glassmorphic dark interface.

---

## Key Concepts Learned

### 1. Unified Navigation Shell & Outlet Architecture
Instead of re-rendering full layouts or repeating header/sidebar components across screens, Phase 7 uses React Router v6 nested routes inside a root layout (`Shell.jsx`).

```jsx
// App.jsx routing topology
<Routes>
  <Route path="/login" element={<Login />} />
  <Route element={<Shell />}>
    <Route path="/dashboard" element={<Dashboard />} />
    <Route path="/emails" element={<EmailInsights />} />
    <Route path="/dayplan" element={<DayPlan />} />
    <Route path="/chat" element={<Chat />} />
    <Route path="/nightsummary" element={<NightSummary />} />
  </Route>
</Routes>
```

`Shell.jsx` maintains navigation state, active tab highlighting (`cyan #00d9ff` accent glows), and common branding, delegating screen content to `<Outlet />`.

### 2. State-Driven Authentication & Timetable Wizard Flow
First-time user onboarding vs returning user authentication is governed dynamically:
- Upon mounting `/login`, `Login.jsx` issues `GET /api/timetable`.
- If HTTP 401 (no OAuth token) or count > 0: user is marked as returning and shown "Continue with Google".
- If HTTP 200 + count === 0: user is routed into the interactive timetable setup wizard.
- **Refresh Survival**: Starting timetable setup writes `sessionStorage.setItem('sevaSetupInProgress', '1')`. If a page refresh occurs during setup, `Login.jsx` reads this key to preserve setup state without bouncing back to Google OAuth. Upon submitting the timetable, `sessionStorage.removeItem('sevaSetupInProgress')` clears the guard.

### 3. Client-Side Cross-Referencing & Bidirectional Task Completion
Plan items generated by LLMs (`plan_json`) do not natively store SQLite `task_id` primary keys. `DayPlan.jsx` implements client-side task cross-referencing:
- Normal tasks are matched by normalized lowercase name comparison (`cleanPlanName === task.name.trim().toLowerCase()`).
- Toggling task completion issues a `PATCH /api/tasks/:id/complete` request with payload `{ completed: 0 | 1 }`.
- Inline events (e.g. `surprise_event` injected during replanning) with no corresponding DB task row disable the checkbox with an informative tooltip (`"Inline event (no separate task row)"`), preventing UI crashes or orphaned API requests.

### 4. Direct Feed Optimism & In-Flight Action Protection
To ensure fluid UX during long LLM calls (30–60 seconds for plan generation and chat responses):
- **Optimistic Updates**: User chat messages render immediately in the conversation thread before backend round-trips resolve.
- **In-Flight Action Locking**: Email accept/dismiss buttons and plan generation buttons lock themselves into disabled loading states (`isAccepting`, `isGeneratingPlan`) to prevent duplicate form submissions or race conditions.

## Known Limitations

1. **Client-Side Name Matching for Plan Tasks**: `DayPlan.jsx` matches timeline items to SQLite task rows using string normalization (`task.name.trim().toLowerCase()`). If an LLM rewrites task titles during planning, matching fails gracefully by disabling completion checkboxes.
2. **Local AI Wait Durations**: Local LLM inference via Ollama takes 30–60s per generation call. All screens handle this via explicit loading states and disabled controls.
3. **Date-Scoped Chat View**: Chat history is loaded for the current active date. Viewing multi-day past transcripts requires date selection enhancements in future phases.

## Important Interview Questions & Answers

**Q1: How does your React application maintain design consistency across multiple complex screens?**  
**A1:** We established a centralized Design Token system in `themeUtils.js` and custom Tailwind variables. Priority levels (`high`, `medium`, `low`) and event badges (`meeting`, `deadline`, `opportunity`, `general`) map to predefined HSL color tokens and CSS classes (`getPriorityBadgeClass()`, `getEventTypeBadgeClass()`). All screens import these utilities rather than duplicating inline color logic.

**Q2: How did you handle user refresh attempts during multi-step onboarding?**  
**A2:** During the OAuth and timetable wizard setup on `/login`, we write a temporary key `sevaSetupInProgress = '1'` to `sessionStorage`. When the page reloads, `useEffect` reads this flag prior to running network authentication checks, returning the user immediately to the active wizard step. Upon successful submission to `POST /api/timetable`, the session flag is explicitly removed.

**Q3: How do you prevent race conditions when users interact with slow AI actions like plan generation or email syncing?**  
**A3:** Every screen enforces strict state locking (`isGeneratingPlan`, `isAccepting`, `isReplanning`). Action buttons trigger an immediate UI loading state, rendering spinning indicator badges and disabling the button DOM elements (`disabled={loading}`) for the duration of HTTP requests.

**Q4: How does task completion toggling work between the Day Plan timeline and SQLite database?**  
**A4:** `DayPlan.jsx` cross-references plan items against the array returned by `GET /api/tasks`. Clicking a task checkbox calculates `newCompletedStatus = matchedTask.completed === 1 ? 0 : 1` and fires `PATCH /api/tasks/:id/complete` with `{ completed: newCompletedStatus }`. The backend updates SQLite and returns the fresh state, allowing smooth two-way completion toggling.
